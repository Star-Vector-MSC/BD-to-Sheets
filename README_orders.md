# Заказы WB: обновление в 08:00 и 20:00 МСК

`orders.local.json` задаёт внешний файл credentials и список листов; начните с `orders.example.json`. Каждый элемент содержит ID таблицы, числовой gid и точное название **уже существующего, принадлежащего выгрузке** листа. Скрипт не создаёт листы автоматически. Заголовки и сетка из семи колонок должны совпадать; неизвестное содержимое он не заменяет.

## Расчёт

Скользящий период: последние 30 **полных** дней по Москве, без текущего дня. Период пересчитывается при каждом запуске.

- FBS: `COUNT(DISTINCT task_id)` из `assembly_task`; EXISTS текущего статуса из `status_assembly_task`, исключая `declined_by_client`, `canceled`, `canceled_by_carrier`, `canceled_by_client`. Отсутствующий или NULL-статус не проходит фильтр.
- Сначала выбираются группы «дата + wild» с такими FBS-заданиями. Сохраняются все ненулевые артикулы WB внутри этих групп, включая артикулы только с воронкой/FBO.
- Воронка: сумма `funnel_daily.order_count` по дате и `nm_id`.
- FBO: `GREATEST(funnel_orders - fbs_qnt, 0)` **для каждого nm_id**. Сумма после такого обнуления иногда выше FBO, рассчитанного после сложения по wild. Это ожидаемая неаддитивность; число групп и разница записываются в отчёт.
- Колонки: `date`, `nm_id`, `wild`, `fbs_qnt`, `fbo_qnt`, `funnel_orders`, `updated_at`. Идентификатор WB — текст. Время снимка едино для всех целевых листов.

SQL находится в `sql/`. В одной транзакции REPEATABLE READ, только на чтение, выполняются детальная выборка и независимый исходный расчёт по wild. До записи должны совпасть наборы групп, FBS и воронка по каждой группе. Проверяются уникальность ключей, соответствия nm_id → wild и формула FBO.

## Запуск

```powershell
.\.venv\Scripts\python.exe -B export_orders.py --settings orders.local.json
.\.venv\Scripts\python.exe -B export_orders.py --settings orders.local.json --apply
```

Первый вызов проверяет данные и целевые листы, без записи в Google Sheets. Второй обновляет все заданные листы из одного снимка: предварительно проверяет оба назначения, сохраняет прежнее содержимое, заменяет значения A:G блоками, убирает устаревший хвост и сокращает сетку, затем перечитывает **все** записанные значения. Остальные листы не меняются.

Google Sheets не предоставляет транзакцию между двумя таблицами. При сбое второго назначения первое могло обновиться; последний общий успех не меняется, промежуточный прогресс записывается. Следующий успешный запуск приводит оба листа к одному новому снимку. Не редактируйте и не сортируйте принадлежащие выгрузке листы во время выполнения.

## Расписание Windows

```powershell
powershell -ExecutionPolicy Bypass -File .\install_orders_task.ps1
```

Установщик требует часовой пояс Windows `Russian Standard Time`. Задача `WB Orders to Google Sheets - Daily 08 and 20 MSK` запускается ежедневно в 08:00 и 20:00 МСК, двумя ежедневными триггерами без почасового повторения. При миграции прежняя почасовая задача удаляется только после успешной регистрации новой и проверки принадлежности проекту; её XML сохраняется в `runs/orders-previous-task.xml`. Используется `pythonw.exe` из `.venv` проекта; видимого окна нет. Три повтора через пять минут при ошибке, ограничение одного запуска 30 минут, новые параллельные экземпляры запрещены. Пропущенный запуск выполняется при доступности, разрешено пробуждение.

**Компьютер должен быть включён, а пользователь — войти в Windows.** Это локальное расписание; публикация исходников в GitHub не запускает их на сервере. Существующая задача платежей не меняется.

```powershell
Start-ScheduledTask -TaskName 'WB Orders to Google Sheets - Daily 08 and 20 MSK'
Get-ScheduledTaskInfo -TaskName 'WB Orders to Google Sheets - Daily 08 and 20 MSK'
Get-Content .\runs\orders.log -Tail 5
```

После успешного контрольного запуска ожидается `LastTaskResult = 0`. `runs/orders-last-success.json` содержит время, период, число строк и подтверждение полной проверки всех назначений. Предыдущие снимки и файлы текущего запуска также лежат в `runs/`, исключённом из Git. В журнал ошибок не выводятся тексты драйверов с возможными credentials.
